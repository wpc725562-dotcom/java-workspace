# 为什么这个目录现在是空的

**这不是遗漏，是有意的。**

## P3 和 P0–P2 的做法不一样

P0 / P1 / P2 是「选定一个开源项目 → 完整吃透 → 改造成自己的」，
所以它们各自有一个明确的克隆目标，代码就在隔壁目录。

P3 不是。计划里 P3 的结论是：

> 不要「跟着一个课程再抄一遍秒杀」。正确姿势是：先读三个开源实现的
> 限流 / 缓存 / 队列方案，输出对比表，再自己实现核心链路。
> **P3 的产出是一份「方案对比 + 我的选择及理由」，而不是第四个练手项目。**

所以 P3 需要的是**三个**仓库、而且是**读**不是**改**，还要在读完之后自己写一版。
在读到那一步之前，先挑哪三个、以及要不要保留哪几个，都还没有定论。

## 为什么现在不预先克隆

1. **时间上太远。** P0(6 周) + P1(6 周) + P2(4 周) = 16 周，P3 在第 17 周之后。
   现在就把它拉下来，四个月里它只是一堆不会打开的文件。
2. **选型还没定。** 候选至少有这些，且质量分布和直觉相反：

   | 仓库 | Star | 体积 | 最后推送 | 许可证 | 备注 |
   |---|---|---|---|---|---|
   | `qiurunze123/miaosha` | 26,592 | 64.2 MB | 2025-04-18 | 无 | 最高星，README 自称「停更」 |
   | `zaiyunduan123/springboot-seckill` | 3,293 | 4.9 MB | 2022-03-06 | 无 | 已停更 4 年 |
   | `codingXiaxw/seckill` | 2,166 | 21.0 MB | 2022-12-16 | 无 | 慕课网课程复刻 |
   | `lyrric/seckill` | 1,946 | 273 KB | 2025-12-19 | 无 | 体积很小，偏教学骨架 |
   | `gongjunhao/seckill` | 1,946 | 3.1 MB | 2021-01-06 | MIT | **唯一有明确许可证的** |
   | `hfbin/Seckill` | 1,427 | 4.1 MB | 2024-04-18 | 无 | — |

   **7 个仓库里只有 1 个有许可证。** 这意味着读到的实现大多**不能直接复用** ——
   但反过来，这正是它能产生差异化的原因：没有成熟参考，你的方案就是你自己的。

3. **秒杀类参考实现比商城类少一个量级。** 商城类最高 `macrozheng/mall` 84,839 star
   且仍在推送；秒杀类最高 26,592 且多数停在 2021–2022。
   所以「读三个实现」这件事本身信息量就有限，更要挑得准。

## 到 P3 时要做的事

```bash
# 从候选里挑 3 个（建议覆盖不同的技术路线，而不是三个都差不多）
git clone --depth=1 https://github.com/<owner>/<repo>.git p3-seckill/<repo>

# 重点读这三块，每个仓库做一张表
#   ① 库存扣减：数据库行锁 / Redis 预减 / Lua 脚本 / 消息队列，各自怎么防超卖
#   ② 限流削峰：令牌桶 / 漏桶 / 消息队列缓冲 / Nginx 层限流
#   ③ 一人一单与缓存一致性：怎么防重复下单，缓存和数据库怎么对齐
```

产出物 = **方案对比表 + 我的选择及理由**，放进 `D:\WorkBuddy\...\outputs\`，
和 P0–P2 的报告放一起。核心链路自己写，不要抄。

## 为什么技术点不重复

商城你已经做过两遍了（P0 的后台管理 + P2 的微服务电商）。再做一遍商城，边际收益接近零。

秒杀逼你处理的是**另一类**问题：库存原子扣减、一人一单、防超卖、限流削峰、
缓存与数据库一致性。这些是面试高频点，也是让你从「做过 CRUD」变成
「处理过并发问题」的分水岭 —— 对赴日就职来说，「高并发下的数据一致性」
是通用能力，日本 SIer 现场也认。
